Dedupe Tool

A RevOps tool that finds duplicate people and companies across CRMs and files, and decides which data survives each merge based on what each field means, not on a rule per field.

My role
Product design, architecture and build
Built with
  • TypeScript
  • Next.js
  • Postgres
  • Vitest
  • Render

How it works

  1. 1Duplicates
  2. 2Match ≥ 0.95
  3. 3Field tags
  4. 4Clean record

→Every surviving value has a reason

The business problem

Pressing “merge” is easy. The hard part is making sure the right data survives every merge.

Example: Dana filled in a pricing-demo form in 2023. In 2025 an SDR cold-called her and created a second lead. After the merge you want how she first arrived (web form, the campaign) kept from the old record, the latest outbound owner and sequence from the new one, her current title, the strongest lifecycle stage she reached, and all her interests combined.

Existing tools make you pick a master record and write a rule per field, and whatever loses is deleted. The logic has to be right up front and can’t be changed later. Attribution data, which marketing reports depend on, is usually the first casualty.

I lived this in RevOps. Duplicate cleanup was one of the team’s most time-consuming jobs, and sales leadership couldn’t understand why it kept happening or why it was such a headache. A lose-lose situation: RevOps burned hours, and leadership lost trust in the data.

How I read the requirements

RevOps people think in terms of what a field means (“how they first came in”, “who’s working them now”), not in per-field algorithms. So the product had to speak that language, and every resulting value had to be explainable in one sentence.

Key decisions and trade-offs

1. Tag meaning, don’t write rules. Each field gets one tag: origin (earliest value), current (latest non-empty), channel (earliest or latest from one channel, like inbound or outbound), strongest (highest in a ranking you give), or combine (all distinct values). About six tags cover almost every field, and tags are pre-filled from field names (“First_…” suggests origin), so setup is mostly confirming guesses. Every clean value comes with its reason, for example “Earliest inbound value (2023-03-01), from L-001”.

2. Keep small candidate slots, not full history. Storing every value ever seen would let you change the logic later, but it’s heavy and grows with every update. Instead, each duplicate group keeps a few slots per tagged field: earliest and latest, earliest and latest per channel, and distinct values only where needed. Size is bounded by groups × fields × a few slots, about a few hundred MB for 100k duplicate groups, not by how often records change. Retagging a field later just reads a different slot. The trade-off, written down: changing a channel definition only applies going forward.

3. Merging is order-independent. Combining slots is commutative and associative, with ties broken by source id, so the result never depends on sync order.

4. Quiet by default. High-confidence groups merge automatically. People only see an inbox of exceptions, with records side by side, the proposed clean record, and a reason per value.

5. Examples are tests. A corrected duplicate can be saved as an example. Before a logic change goes live, a preview shows what would change and which saved examples would break.

6. The engine knows nothing about any CRM. A pure TypeScript core with no I/O, so every rule is unit-testable and the same code runs in the CLI, the web preview and later the background worker. CRMs and files are connectors behind one interface.

How I handled risk

Risk Mitigation
CRM merges can’t be fully undone Snapshot before every merge, sandbox first, dry run by default
Wrong auto-merges destroy trust in the tool Auto-merge only at confidence ≥ 0.95; a shared free-email domain is never a match signal; a group is only as confident as its weakest link
Changing logic silently breaks past decisions Preview impact before save; saved examples act as regression tests; decisions on unchanged groups are kept
History from before the tool is partial Backfill from date and source fields, campaign members and form submissions, and mark those values as reconstructed
Bad input data Config and CSV validated at the boundary, with every problem listed in plain words
API rate limits Bulk APIs, per-connector rate budgets, resumable jobs (planned)
Code quality drift Strict TypeScript, 80% coverage gate on lines, branches, functions and statements, CI on every push

Every major choice is recorded as an architecture decision record, including what it costs.

Architecture

packages/core   pure engine: normalize → match → group → candidate slots → clean record + reasons
packages/cli    CSV in, clean CSV out (auto / review tier per group)
apps/web        Health · Inbox · Logic · Data, on Postgres

Outcome

Phases 0 to 2.7 are shipped: the engine, a CSV command line, and a web app that previews duplicates per object, supports overrides and bulk actions, and plans merges. Live CRM write-back is the next phase.

What’s next

CRM connection with background sync and undo snapshots, then lead-to-account matching and a health dashboard with a chat digest, then hardening for 1–5 million records.
