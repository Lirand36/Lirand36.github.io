Deal Intel

A forecast and deal-health app on live CRM data, built around two questions - "will we hit the quarter, and which deals decide it?" for the revenue leader, and "what's the one thing I should do today?" for the rep.

My role
Designed and built end to end
Built with
  • Next.js
  • TypeScript
  • HubSpot API
  • Vitest
  • Render

How it works

  1. 1CRM activity
  2. 26 signals
  3. 3Score 0–100
  4. 4Today's action

→One deal, one next step, every morning

The business problem

Pipeline reviews tend to run on gut feel. A deal “feels good”, the close date slides a month, and nobody notices until the quarter is gone. The CRM already holds the evidence (who is involved, when the buyer last engaged, whether meetings happen), but nobody reads it deal by deal.

I saw first-hand how not connecting the dots fails the people who need it most. The data that would help account executives perform better and win more already existed, spread across different systems, but it never came together into one clear grade and one clear next step.

How I read the requirements

I started from the people, not the data: one question per audience.

Audience Their question Page
Revenue leader Will we hit quota this quarter, and which 3 deals decide it? Quarter
Account executive What’s the one action to take today, and on which deal? My day

Everything else (all deals, won vs lost, pipeline health, the scoring rubric) sits one level down under “More”. If a page didn’t answer one of the two questions, it didn’t make the front.

Key decisions and trade-offs

1. A transparent rubric, not a black-box model. Every deal gets a 0–100 score from six buyer-engagement signals: multi-threading, recent activity, meetings held, days since last touch, close-date slips, and a next step. Each signal has fixed bands and a one-line “why” (for example, “Deals with several buyer contacts survive a champion leaving or going quiet”). A rep can see exactly why a deal scored 45 and what would move it.

2. Score closed deals as they stood on their close date. That makes the “Won vs lost” page honest: it shows which signals actually separated wins from losses in this pipeline, written as plain sentences (“Deals with 2+ people won 73%. Deals with one won 14%.”). The rubric can then be checked against reality instead of assumed.

3. Overdue deals stay in the current quarter. Open deals whose close date has already passed are counted in the current quarter. Leaving them out would quietly hide slipped pipeline; the rep still has to close or move them.

4. One action per deal, strongest risk first. Each deal gets the first play it qualifies for, and a passed close date always comes first, because the forecast is wrong until it’s fixed.

5. Account briefs that separate fact from opinion. Each action opens a brief: company, buying group, and a SWOT where every line is tagged evidence or our read, plus what the brief can’t see.

How I handled risk

Risk What I built
Wrong or malformed CRM data breaks the scores All CRM responses are validated and mapped in one place before the scoring engine sees them
Scoring logic drifts or regresses The scoring engine is pure (no I/O) and fully unit-tested; lint, typecheck and coverage run before every change
Demo data contaminates a real CRM The seed script tags every record it creates, and an unseed script moves exactly those records to the recycle bin. The docs say to use a test portal.
Exposing deal data publicly Login with an admin password (12+ characters), generated session secret, rate limiting
A demo that needs credentials to show anything Demo mode with generated sample deals; adding a CRM token later switches it to live data
Least privilege The app’s CRM token needs read scopes only; write scopes are needed just for the seed script

Architecture

CRM (deals, contacts, companies, activities)
  → one I/O module + validation / mapping
  → pure core: score · forecast · win factors · actions · brief
  → pages: Quarter · My day · More

Outcome

A deployed app that runs on live CRM data or on demo data, with a forecast a leader can question line by line and a daily action list a rep can actually work through.

What I’d do next

  • Recalibrate the rubric weights from the won-vs-lost results once there’s enough closed history.
  • Push the daily action to where reps already work (chat or the CRM task list) instead of a separate page.
